# 技术文档

本文档记录项目的阶段进展、后续期望与 Docker 容器化部署的设计说明。

## 项目阶段

目前阶段完成情况：

1. **RAG 检索链路升级（P0→P4）已完成并定格**：最终生产链路为 `dense(20) + bm25(20) → RRF(rrf_k=60, topn=20) → gte-rerank-v2 精排 top_k=5`；查询优化（multi_query / HyDE）与「融合后统一精排」变体已实现，经评测无净收益，默认关闭，仅作可选实验开关保留；
2. **格式感知分块已完成**：支持 `pdf` / `docx` / `doc` / `txt` / `md` / `xlsx` 六类格式，按扩展名路由到对应解析器（`doc` 复用 docx 解析），结构化格式额外做超长切分与小单元合并；chunk 携带章节路径与页码元数据，供检索与引用溯源使用；
3. **参数热更新已完成**：设置页保存后写入 `retrieval_config.yml`、同步内存配置并重建检索单例，检索参数无需重启即时生效；变更记录 `before→after` 审计日志；
4. **引用溯源已完成**：回答与引用来自同一次检索结果，按文档去重，引用携带章节路径、页码区间与正文片段；
5. **评测体系已完成**：自建 retrieval-only 评测框架（评测集 v1 80 题 / v2 260 题，报告对比与归档），支撑链路组合的 A/B 对照；最终 v2 集文档级 HitRate 0.8115、片段级 HitRate 0.7846、内容召回率 0.7881，全程零幻觉；实验报告归档于 `docs/rag_eval_reports/`；
6. **模型双模式已完成**：`MODEL_MODE` 一键切换远程 API / 本地 Ollama，聊天模型可自定义为任意 OpenAI 协议供应商，嵌入/精排/评测模型默认走 DashScope；
7. **前端页面与后端业务接口全部完成并已联调**：登录、主框架、Bot 问答、知识库、统计数据、系统设置（含检索增强参数区块）、账号管理均已对接真实接口；
8. **账号管理模块重构已完成**：关闭自由注册，改为单租户 + `admin` / `user` 两级角色（普通用户含 L1/L2/L3 三档能力）；管理员由 `ADMIN1..3_*` 环境变量在启动时初始化（已存在不覆盖密码），普通账号由管理员创建，账号名统一为 `czzsk` + 6 位补零自增 id；随机初始密码仅显示一次，支持重置密码、启停、软删除；权限判定收敛到后端 `permissions.py` 并由 `require_permission` 依赖统一拦截（知识库写、RAG 参数、账号管理均已收紧），前端仅做菜单与按钮隐藏；账号体系、权限矩阵与运维说明见 [`账号管理说明文档.md`](账号管理说明文档.md)；
9. **单元测试**：共 535 个用例覆盖工具/模型/核心/数据/依赖/服务/路由/Agent/评测各层，全部 mock 外部依赖（MySQL/Qdrant/DashScope/LLM/Ollama），未启动 Qdrant 容器亦可全部通过；运行方式详见 `tests/README.md`；
10. **后续可迭代**：详见下一章「项目期望」。

## 项目期望

当前版本已具备「私有知识库 + 混合检索 + 精排 + 引用溯源 + 评测闭环」的完整能力。后续按优先级推进以下方向：

### 1. RAG 链路精细化迭代（低风险高收益，依托现有评测框架做 A/B）

在现有 hybrid → RRF → rerank 主干上收敛优化，不推翻架构：

| 方向 | 说明 |
|---|---|
| 差异化分块 | 按文档类型/章节粒度自适应切分，减少跨章节语义截断 |
| 查询分类 / 子问题拆解 | 先判定问题类型（事实型/对比型/多跳型），再决定检索路数与是否拆解 |
| 多路召回增强 | 在 dense + BM25 之外引入元数据（部门/时间/文档类型）召回，一并参与 RRF |
| 参数自适应 | 按 query 复杂度动态调整 `dense_topn` / `topn` / `top_k` |
| rerank 动态阈值 | 按精排分数分布截断，低置信度片段不送入生成，抑制幻觉 |
| 证据溯源与幻觉校验 | 生成后逐句回查证据片段，无支撑内容显式降级为「未检索到」 |

所有改动必须先在自有评测框架上跑对照实验，指标不退化才进入默认链路。

### 2. 知识图谱增强（可选，按需启用，不替换现有 RAG）

采用**路由 + 并行召回融合**方案，与现有链路并存：

- **轻量版**：实体抽取 + 实体与 chunk 绑定，命中实体时扩展召回候选；
- **完整版**：构建三元组图谱，支持图检索（关系查询、多跳推理）；
- **融合方式**：关系/多跳类问题由路由分发给图谱工具，普通文本查询仍走 hybrid + rerank；图谱结果可并入候选池共同参与 RRF + 精排；
- **评测**：单独建立图谱评测集，指标达标后再按需启用，避免盲目上线。

### 3. 其他可补充方向

- **多模态检索增强**：图纸、截图、表格、流程图经 VLM / OCR 解析后入库，纳入检索池；
- **Redis缓存增强**：高频向量查询、热门问答上下文缓存，降低向量库与LLM重复调用开销，支持会话状态快速读写；
- **文档治理与增量流水线**：增量更新、版本快照、变更自动重索引、脏文档过滤；
- **权限感知检索**：文档分组与行级权限过滤，检索时自动剔除无权限 chunk（账号模块已完成，可在此之上扩展）；
- **全链路可观测与 Badcase 闭环**：Trace 日志、失败案例归集、用户正负反馈回流评测集；
- **模型动态路由与成本调度**：embedding / rerank / LLM 多模型池，按查询复杂度自动选模型；
- **记忆与会话上下文增强**：Agent 侧长期记忆、实体上下文继承、历史 query 压缩，减少重复检索；
- **知识库配套工具**：文档摘要生成、文档对比、版本差异检索、条款变更识别；
- **自我校验与反思增强**：Agent 内部证据自检、冲突检测、多轮二次检索自省；
- **部署与运维**：CI/CD 流水线、Kubernetes 编排、数据备份恢复策略。

## Docker 容器化部署

### 架构概览

```
互联网用户 → Nginx(:18080) → Frontend Vue(:13000)  静态页面
                          → Backend API(:18000)  数据处理
                                   ↓
                          MySQL(:16666→3306)   关系型数据库
                          Qdrant(:16333→6333)  向量数据库
                          Ollama(:21434→11434) 本地模型服务（MODEL_MODE=local 时使用）
```

> 用高位端口是为了预防端口占用问题，详见 [`常见报错问题解决方案速查.md`](常见报错问题解决方案速查.md)。

### 两种使用模式

本项目支持两种 Docker 使用模式，启动步骤见 README「安装运行指南」，此处仅说明两种模式的特点与适用场景：

#### 模式 A：基础设施模式（推荐开发阶段使用）

- 只启动 MySQL 和 Qdrant 两个基础服务，前后端在本地（Windows）运行；
- 代码修改即时生效（后端热重载 + 前端 HMR），支持 IDE 断点调试；
- 资源占用少、启动速度快；需本机安装 Python / Node.js 依赖。

#### 模式 B：完整容器化模式（部署/演示阶段使用）

- 一键启动全部 5 个服务（MySQL、Qdrant、Backend、Frontend、Nginx），环境一致性高；
- 无需本机安装 Python / Node.js 依赖，适合演示、测试环境与生产部署；
- 修改代码后需重新构建镜像，构建/拉取耗时较长。

#### 模式对比

| 对比项 | 模式 A：基础设施模式 | 模式 B：完整容器化模式 |
|---|---|---|
| 启动服务 | MySQL、Qdrant | 全部 5 个服务 |
| 代码运行位置 | 本地（Windows） | 容器内 |
| 代码修改生效 | 即时（热重载） | 需重新构建 |
| 调试支持 | IDE 断点调试 | 日志查看 |
| 适用阶段 | 开发调试 | 部署/演示/生产 |
| 资源占用 | 较低 | 较高 |
| 依赖安装 | 需本地安装 | 无需本地安装 |

### 关键设计说明

| 设计点 | 说明 |
|---|---|
| 业务配置 vs 部署配置 | `backend/app/config/` 存放业务级 YAML 配置，`docker/` 存放部署级配置，职责分离 |
| 独立 Dockerfile | `backend/Dockerfile` 和 `frontend/Dockerfile` 各自管理构建，不混入 docker 目录 |
| 多阶段构建 | 后端使用 `uv` 官方镜像构建虚拟环境后复制到 slim 运行镜像；前端使用 Node 构建后由 Nginx 托管 |
| 健康检查 | 所有服务均配置 healthcheck，后端依赖 MySQL/Qdrant 健康状态后才启动 |
| 环境隔离 | 通过 `--env-file` 切换 `.env.dev` / `.env.prod` 实现开发/生产环境分离 |
| 运行时配置可写副本 | `backend/app/config` 仍以 `:ro` 挂载作为出厂默认值；启动时把 `retrieval_config.yml` 复制到 `RUNTIME_CONFIG_DIR`（`/app/runtime_config`，命名卷 `privrag_rag_config`），设置页只写副本，解决只读挂载导致保存 RAG 参数失败，且容器重建后参数不丢 |
